# 跟踪滞后：现状、根因与技术方案

> 日期：2026-10-23　基线：`main@70f8fee`
> 关联文档：[K230_ESP32_UART.md](K230_ESP32_UART.md)（第 7 节已有一次前视尝试）、
> [LASER_HEATMAP.md](LASER_HEATMAP.md)、[ARCHITECTURE.md](ARCHITECTURE.md)
>
> **2026-10-23 实测补充**：电脑同时直连 K230(`/dev/ttyACM0`) 与 ESP32(`/dev/ttyUSB0`)
> 后，已用 `tools/track_latency_probe.py` + `tools/gimbal_step_probe.py` 量到真机数据，
> 见 **[第 8 节](#8-真机实测2026-10-23)**。结论有两条要马上改口：
> ① **`jpeg_every` 基本没用**，真正卡住控制环的是**每帧编码像素数**
> （`enc_scale 0.8→0.5` 让 AI 帧率 4.9→12.3 Hz）；
> ② 把 AI 改成每帧跑（`ai_every=1`）本身只能到 8.2 Hz，**必须同时降编码像素**。

本文回答三个问题：**滞后从哪来**、**别人的成熟做法是什么**、**我们按什么顺序改**。
结论先行：**纯靠"把检测做快"补不回这个延迟，必须做"时延补偿（预测）+ 控制律改造"；
而做补偿的前提是拿到每一帧的"拍摄时刻"时间戳——这正是 7.3 节那次世界系前馈
失败的原因。**

## 1. 现状：链路里已经知道的事实

| 环节 | 实测 | 出处 |
| --- | --- | --- |
| 采集（640×480 双通道） | 57 fps，17.5 ms/帧 | `board/k230_perf.py` 头注释 |
| Pose 384 推理 | 40~43 ms | 同上 |
| Pose 256 推理 | 约 30 ms（本次新增，`pose_v3_256.kmodel`） | 待实测 |
| 小靶 ROI 复筛 | 单帧 +45~50 ms（`low_refine`，只在大框时触发） | `yolo_pose.py` |
| JPEG 编码（回传用） | 640×480 65~78 ms，512×384 52~58 ms | `k230_perf.py` |
| UART `$KT`（115200，单帧几十字节） | <1~2 ms | — |
| ESP32 控制环 | 100 Hz（LEDC 直写后） | UART 文档 7.1 |
| 舵机 50 Hz PWM + 机械响应 | 数十 ms 量级 | — |
| **控制量更新率** | `ai_every=2` 时**半帧率**（板端 20~26 fps → 目标 10~13 Hz） | `yolo_pose.py` CFG |
| 真机跟踪误差（2026-10-19） | 静止 6 px / 慢移 21 px / 快移 **53 px（P95 ~160 px）** | UART 文档 7.3 |

已有的一版补偿：ESP32 侧"图像系 PID + 速度自适应前视"
`err = (x + vx·leadEff) − 320`，`leadEff = 0.2s × clamp(|vx|/500, 0.7, 1.2)`，
把高速跟踪 RMS 从 99.6 px 压到 37~49 px；但**加大前视反而更差**
（0.35 s → 84 px vs 0.25 s → 69 px），世界系速度前馈试过并放弃
（"依赖拍摄时刻的云台角度，capdel 差 30 ms 就发散，拿不到精确时间戳"）。

这两条失败记录是本文最重要的输入：**不是"预测"这个方向错，而是当时的
数据和时间基准不足以支撑预测。**

## 2. 滞后预算（先算清楚，再动手）

端到端延迟 = 目标出现在真实世界的时刻 → 舵机真正转到位的时刻。

```
拍照时刻 t0
  + 传感器/VICAP 缓冲（固件双通道，约 1~2 帧）    ~20~35 ms
  + AI2D 预处理 + 推理（384）                     40~43 ms
  + 后处理 / 复筛（仅小靶触发）                    0~50 ms
  + 板端其他同步工作（激光、绘制、JPEG 若同线程）  0~70 ms（当帧恰好编码时）
= 数据可用 t1，此时"已经旧了" Δ1 = t1 − t0       合计 60~150 ms
  + UART 传输                                      1~2 ms
  + ESP32 PID/滤波（前视只补一部分）                10~30 ms
  + 舵机 PWM 周期 + 机械到位                       30~60 ms
= 真正到位 t2，总延迟 Δ2 = t2 − t0               ≈ 100~200 ms
```

**关键判断**：即使把推理从 40 ms 压到 20 ms，Δ2 也只降 20 ms——对"快速任意方向"
这种场景（目标 1 s 扫过全屏 ≈ 600 px/s），20 ms 只值 12 px，而当前误差是 53 px。
所以 **Δ2 里最适合补的是 t0→t1 这一段"已知但当前未使用"的信息**：只要知道
每帧的 t0，就能把目标外推到 t2，把 100~200 ms 的滞后换成"预测误差"。

> 这就是"预测补偿"与"提高帧率"的本质区别：前者用信息换延迟，后者用算力换延迟。

## 3. 外部资料与可借鉴项目

### 3.1 为什么"纯卡尔曼平滑"不够：快速小目标的实测结论

* **An Analysis of Kalman Filter based Object Tracking Methods for Fast-Moving Tiny Objects**
  （arXiv 2509.18451，[ar5iv 全文](https://ar5iv.labs.arxiv.org/html/2509.18451)）
  在 10000 帧快速小球数据上比较 OC-SORT / DeepOCSORT / ByteTrack / BoT-SORT / StrongSORT：
  * 五个跟踪器**全部**基于常速卡尔曼，对"快速 + 频繁变向"的小目标 ADE 31~114 px；
  * ByteTrack 处理最快（26.6 ms）但 ADE 最差（114 px），DeepOCSORT 最准（31 px）；
  * 作者结论：**匀速模型对非线性运动不够**，需要"观测中心"修正/物理先验或更合适的模型。
  → 对我们的意义：`PointKalman` 的常速模型在上一次前视尝试里"加大前视更差"，
  与这篇的结论一致；**要预测就得上带阻尼/多模型的预测器**，而不是简单 `x + v·τ`。

* 项目代码：[KFTrackingEvaluation](https://github.com/Prithviraj97/KFTrackingEvaluation)（可复现的评测框架）。

### 3.2 视觉伺服里"预测目标未来位置"的标准做法

* **Predicting a moving object position for visual servoing: theory and experiments**
  （Malis & Chaumette 等，Wiley *Int. J. Adaptive Control & Signal Processing*，
  [DOI 10.1002/acs.628](https://onlinelibrary.wiley.com/doi/10.1002/acs.628)）
  系统讨论"用当前观测外推目标在**若干帧之后**的位置"再做伺服，给出误差传播与
  何时该预测、何时该停的判据。核心结论与我们相关：
  **外推时间越长收益越大，但目标机动时会过冲，必须有"预测可信度/截止"机制。**

* **A Discrete-Command Predictive Control Method for Dual-Axis Gimbal in Anti-UAV Visual Tracking**
  （IEEE [11661553](https://ieeexplore.ieee.org/document/11661553)）
  双轴云台 + 视觉跟踪，直接面向"离散指令 + 检测延迟"的工程场景，
  用预测控制补偿指令离散化与视觉滞后——与我们的 ESP32"每收到一帧 `$KT` 发一次
  舵机指令"的结构几乎一样，**这是最值得照抄思路的一篇**。

* **Adaptive Gimbal Tracking via Detection-Uncertainty Modeling and LQR‐PID Predictive Compensation**
  （IEEE [11632424](https://ieeexplore.ieee.org/document/11632424)）
  把检测不确定性（置信度/框抖动）引入"该补多少"的自适应增益，再做 LQR-PID
  预测补偿。对应到我们：`conf` 低、`vx/vy` 抖动大时应该**自动缩短前视**。

* 经典视觉伺服综述（Chaumette & Hutchinson, *Visual Servo Control*）中
  "延迟补偿 / 预测"一节：把延迟当作系统的一部分，用"未来时刻的设定值"驱动控制器。

## 4. 方案：三层，按投入产出排序

### L0　先量出"每一段的真实毫秒数"（必须做，1 天）

没有真实延迟数字，后面所有参数都是猜的。要做三件事：

1. **帧时间戳进协议**：板端在 `snapshot()` 返回后立刻取 `time.ticks_ms()` 记为 `t_cap`，
   `$KT` 增加两个字段：`t_cap`（模 2^16 的毫秒）与 `post_ms`（该帧 AI+复筛耗时）。
   ESP32 收到时用自己时钟算"数据年龄"，打印中位数/P95。
2. **端到端标定**：手举靶纸做一次"瞬移 → 静止"，用 ESP32 日志画阶跃响应，
   量出 `视觉延迟 + 控制延迟` 的真实和；再用 IDE 预览录屏数帧，交叉验证。
3. **PC 侧对照**：`k230tool live` 已有 `ms/jpg/loop` 统计，
   但那是"板端处理耗时"不是"端到端延迟"，两者要分开记账。

**产出**：一张"延迟分解表"（替代第 2 节的估算），以及三个可调参数：
`CAP_DELAY_MS`（拍照→可用）、`TX_MS`、`SERVO_MS`。

### L1　压掉不必要的延迟（改动小，收益确定）

| 动作 | 预计收益 | 风险/代价 |
| --- | --- | --- |
| **控制帧与回传帧解耦**：把 JPEG 编码彻底挪出 `$KT` 的关键路径（当前已是"先 UART 后 JPEG"，但同一线程仍会串行占用；`jpeg_every` 增大到 3~4 试试） | 减少当帧 0~70 ms 抖动 | PC 预览帧率降，不影响识别 |
| **`ai_every` 从 2 → 1**（仅当推理能压到 ~30 ms） | 控制量更新率翻倍，延迟减半 | 需要 L2 的模型/裁剪先到位 |
| **256 模型替代 384**（已编译 `pose_v3_256.kmodel`） | 推理 −10~13 ms/帧 | 精度待评测（AGENTS 记录 384 更优：远小靶 2.28 vs 3.01 px），**只在追快速目标时切** |
| **小靶复筛移出控制路径**：复筛结果只用于"确认"，不阻塞当帧 `$KT`（用上一帧的平滑值先发） | 去掉偶发 +50 ms | 小靶确认瞬间会晚一帧 |
| **`$KT` 发送频率不低于推理频率**（现在就是）；空目标时也发 `run=0` + 预测位置 | 丢帧时不僵住 | — |

L1 做完，Δ2 大约能降 30~50 ms，但**不足以消除"快移 53 px"**——继续看 L2。

### L2　预测补偿：让"旧数据"变成"未来时刻的指令"（核心）

把每个 `$KT` 从"当前观测"变成"**预测到舵机生效时刻**的观测"。

**数学**（图像系，像素）：

```
τ = 数据年龄 + TX + 控制/执行延迟   （由 L0 实测，ESP32 侧按帧计算）
s = (x, y, vx, vy, ax, ay)          （板端常速/常加速卡尔曼状态，带时间戳）
aim(t + τ) = x + vx·τ + ½·ax·τ²     （对 τ 做阻尼：τ_eff = τ·k_decay，k_decay 随机动性自适应）
```

落地要点（这是与 7.3 节失败版本的区别）：

1. **时间戳必须来自拍照时刻**，而不是"发串口时刻"或"ESP32 收到时刻"；
   板端时钟与 ESP32 时钟不需要同步，只需"年龄"（收到时刻 − 拍照时刻，跨时钟域用一次握手估计偏移）。
2. **在板端做预测，而不是 ESP32 做**：板端有 `vx/vy` 和帧间隔，能按"目标时刻"外推；
   ESP32 只负责"按指令跟踪"，两者职责分开，调参互不污染。
   也可两者都做：板端预测位置 `bx,by`，同时把 `vx,vy` 带给 ESP32 做前馈（协议加字段）。
3. **自适应前视**：`k_decay` 由三件事决定——
   检测置信度 `conf`、速度估计的协方差（卡尔曼自带 `p11`）、以及最近 N 帧的
   "预测误差"（预测位置与实测位置之差）。**预测越不准，前视自动收短**，
   这正好对应 3.2 里两篇论文的"不确定性加权"，也解释了当年"加大前视反而更差"。
4. **机动检测**：连续两帧速度方向夹角 > 阈值（例如 60°）或加速度突变 → 立即把
   前视清零一帧（"刹车"）。快速变向的目标不能一直外推。
5. **协议升级**：`$KT` 增加 2~3 个字段（`t_cap`、`vx`、`vy`；可选 `ax,ay`），
   ESP32 固件同步改。协议文档同步更新（`K230_ESP32_UART.md` 第 2 节）。
6. **回退开关**：ESP32 一个命令 `lead <ms>` 直接设定固定前视、`lead auto` 用板端预测，
   方便 A/B。

**预期**：如果 τ 估得准（误差 <20 ms），快移误差有望从 53 px 降到 20 px 量级；
变向瞬间仍会有一次过冲，靠第 4 点的"刹车"限制。

### L3　控制律：从"位置 PID"升级为"速度前馈 + 位置闭环"（可选，收益大但改动在 ESP32）

现状是图像系 PID：误差大 → 输出舵速大。它天生"要先看到误差才动"。
工业云台/光电吊舱的常见结构是**级联**：

```
外环（慢）：像素误差 → 期望视线角速度 ω_ref = kp·e + (板端给的 vx/f 前馈)
内环（快）：舵机速度环 → 角速度指令（带加速度限幅）
```

其中 `vx/f`（f = 焦距，像素）就是"目标视线角速度"，这正是视觉伺服里的
image-based 前馈项；`f` 可以用标定板一次量出（或按 FOV 估算）。
好处：稳态无差、对延迟的鲁棒性远好于纯位置 PID；坏处：要能拿到舵机真实位置/速度
（当前 ESP32 靠"指令值积分"近似，7.3 节已证明这在时间基准不准时会发散）。
**所以 L3 一定排在 L0/L2 之后**，且只在 L2 做完、A/B 仍不够时才上。

### L4　硬件/架构（最后考虑）

* **回传链路**：如果"滞后"指的是 **PC/IDE 看到的画面**，那瓶颈是 JPEG 编码
  （65~78 ms/帧）+ USB REPL 带宽，最多 ~11 fps。解法优先级：
  缩小回传分辨率（`roi_scale`/`enc_scale`）→ 隔帧 → 若固件支持硬件 H.264 再考虑。
  这块**不影响控制闭环**，别和云台跟踪混为一谈。
* **板上直控**：K230 自己出 PWM 控舵机（去掉"K230→ESP32→舵机"两跳）。
  ESP32 已经是 100 Hz 实时环，跳到板上的收益主要是省 1~2 ms UART，**不值**；
  除非要上更复杂的控制律（MPC）且 MicroPython 扛不住。
* **舵机**：当前 50 Hz PWM + 普通舵机，机械响应本身就是数十 ms 的滞后。
  数字舵机可上 333 Hz（见 3.3 的 CSDN 文章），但换硬件不在本轮范围。

## 6. 风险与反面清单

* **不要再"凭感觉加大前视"**：7.3 已证明固定大前视会过冲；必须自适应 + 机动刹车。
* **不要用"发串口时刻"当时间戳**：那会把 UART 抖动算进预测；必须用拍照时刻。
* **不要把时钟同步做成硬依赖**：两板时钟只需"年龄"，不需要绝对同步。
* **预测器的模型选择**：常速 Kalman 在目标急停/变向时误差最大（3.1 论文结论），
  可加一个"零速模型"做 IMM（两模型加权），代价是板端多几十行代码；
  先用"预测误差反馈调 `k_decay`"的简化版，不够再上 IMM。
* **JPEG 回传与控制闭合**：`jpeg_every` 调大只影响看，不影响控；别为了"看起来流畅"
  去降推理频率——那会直接增加控制延迟。
* **单线程是硬约束**：K230 上推理、编码、串口都在一个循环里，任何新工作（如激光）
  都要算进"当帧控制路径是否会变长"。激光检测本身是为了闭环精度，
  但如果它把控制帧从 10 Hz 拖到 6 Hz，净效果可能是负的——需要单独 A/B。

---

## 7. 一句话总结

**把"拍到的旧坐标"改成"预测到舵机生效时刻的新坐标"，并且让预测的可信度自己说出来；
在这之前，先把每一帧的"拍摄时刻"和每一段的延迟量出来。**

---

## 8. 真机实测（2026-10-23）

条件：K230 跑 `board/yolo_pose.py`（384 模型）、ESP32 空闲、电脑 USB 同时接两块板；
靶纸**不在视野内**（所以下表的"控制量"是真实 AI 帧节奏，但 `age` 取的是最后一帧的年龄）。
工具：`tools/track_latency_probe.py`、`tools/gimbal_step_probe.py`。

### 8.1 真机数据

| 指标 | 实测 | 说明 |
| --- | --- | --- |
| 遥测包间隔 | **102 ms**（9.8 Hz） | 每帧都发，含非 AI 帧 |
| **AI 帧间隔（`$KT` 更新率）** | **204 ms ≈ 4.9 Hz** | `ai_every=2` 的后果 |
| 推理耗时 | **42 ms** | 384 模型，与文档一致 |
| JPEG 耗时 | **57~60 ms** | 单帧编码 |
| 板端 loop | 122~125 ms | 捕获 + 推理/编码 + USB |
| ESP32 看到的数据年龄 `age` | **中位 105 ms，P95 203 ms** | 目标时刻 → ESP32 可用 |
| 阶跃 slew（80 px 误差） | 约 **200 µs/s** | ≈64 px/s 画面修正（0.32 px/µs） |
| 输出限幅 | pan 740~2260 µs | 一次大误差 1.5 s 即打到限位 |

→ **光子到 ESP32 决策的真实延迟 ≈ 300 ms**（AI 帧周期 204 ms 的一半 + 推理 42 ms
+ 串口/滤波），比第 2 节估算的更差；这直接解释了"快移 53 px / P95 160 px"。

### 8.2 配置对比（同一块板、同一场景，各跑 10 s）

| 配置 | 遥测周期 | AI 帧率 | 推理 | JPEG | loop |
| --- | --- | --- | --- | --- | --- |
| 基线 `ai=2, jpeg=2, enc=0.8` | 97 ms | **4.9 Hz** | 42 ms | 57 ms | 122 ms |
| `ai=1, jpeg=2` | 122 ms | 8.2 Hz | 42 ms | 58 ms | 124 ms |
| `ai=1, jpeg=3` | 122 ms | 8.2 Hz | 42 ms | 58 ms | 123 ms |
| **`ai=1, jpeg=3, enc=0.5`** | **82 ms** | **12.3 Hz** | 42 ms | **32 ms** | **89 ms** |

两个反直觉的结论：

1. **`jpeg_every` 从 2 改到 3 毫无变化**（8.18 → 8.22 Hz）。因为瓶颈是"每帧的
   编码像素数"，不是"多久编一次"——不编码的帧照样被传感器/USB 周期卡住。
2. **只改 `ai_every=1` 反而更慢**（122 ms/帧）：每帧都推理把 loop 顶到 122 ms。
   **必须同时把 `enc_scale` 降到 0.5**，才能拿到 12.3 Hz / 89 ms。

> `enc_scale` 只影响**无目标时的全图**回传；有目标时走 `roi_scale`（默认 0.75）。
> 所以真实目标场景还要把 `roi_scale` 一并降到 0.5 左右，才能复现 12.3 Hz。

### 8.3 由此调整的实施顺序

| 优先级 | 动作 | 实测依据 |
| --- | --- | --- |
| **P1（今天就能做）** | `enc_scale`/`roi_scale` 0.8→0.5 + `ai_every=1` | AI 帧率 4.9→12.3 Hz，loop 122→89 ms |
| P2 | 板端把 `PointKalman` 的 `vx,vy` 和 `t_cap` 塞进 `$KT`（协议加字段） | 现有 Kalman 已经算了速度，只是没发 |
| P3 | ESP32 用 `(t_cap, vx, vy)` 做自适应前视 | 见第 4 节 L2 |
| P4 | 控制律改速度前馈 + 位置闭环 | 见第 4 节 L3 |

**P1 先行的理由**：它不动控制律、不动协议、可回退，直接把"每 204 ms 才看一眼"
变成"每 82 ms 看一眼"——预测器再好，也不如先让数据新鲜一倍。

### 8.5 工作模式实测：常驻代理本身是 19.4 fps（关键修正）

`mode.sh work` 部署的 `gimbal_agent.py` **不做 JPEG 编码**，实测
`agent: 60 frames, 19.3fps` / `120 frames, 19.5fps`（相机已开、模型已载）。
所以：

* **工作模式（真正打靶时）视觉每 ~52 ms 更新一次，不是 204 ms**；
* 8.1 的 204 ms 是 **PC 推流 / IDE 预览路径**（`yolo_pose.py` + JPEG）的数字；
* 结论修正：**打靶时的滞后主因不在"视觉帧率"，而在 ESP32 控制律**
  （固定 0.2 s 前视 + 图像系 PID + 0.32 px/µs 的增益），
  P1 的配置改动主要改善"PC 上看画面 / IDE 预览"的体验，对打靶是次要收益。

下一步应优先做的变成了：

1. 用 `tools/track_latency_probe.py` 在**有靶纸**时量出工作模式的真实
   `age`（预期 ~25~30 ms，比推流路径小一个数量级）；
2. 按 8.4-3 的 0.32 px/µs 重算前视与 `PAN_MAX_RATE`；
3. 若仍慢，再上 L3 速度前馈（§4）。

### 8.4 顺带发现（要修）

1. **K230 常驻代理没有在跑**：实测时板端 REPL 停在 `>>>`，`/sdcard/main.py` 未运行；
   ESP32 的 `$E,START!` 需要**常驻代理**才能被接住。工作模式下 `mode.sh work` 后
   应自动运行，若再次出现"云台不动、K230 不推流"，先查这个（`mode.sh status`）。
2. **ESP32 的 `AIM: bull lost -> DONE` 会把 K230 停掉**：连续 900 ms 没有有效靶心时
   ESP32 会 `gimbal NONE + $E,STOP!`。如果 K230 端因为丢帧/慢帧导致 `$KT` 断流，
   会出现"越丢越停"的正反馈；建议把 STOP 改成"保留 TRACK、只停舵机速度"，
   避免一次短暂丢靶把整条链路关掉（待确认固件当前行为后再改）。
3. **比例尺**：实测 pan 740→1500 µs 只有约 240 px 画面位移（≈0.32 px/µs），
   比文档里 0.6 px/µs 的假设小一半——前视、限幅、死区都要按这个真值重算。
